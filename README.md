Detection Tuning & False Positive Management

During baseline monitoring, legitimate background operations from the sensor node (192.168.1.106) triggered repetitive informational alerts in Suricata. Rather than globally disabling signatures—which would blind detection for the rest of the network—scoped host-based suppressions were applied in /etc/suricata/threshold.config:
Plaintext

# Suppress NetAlertX external IP resolution check (myip.opendns.com) ONLY for the sensor IP.
# Any other internal host attempting to bypass local AdGuard DNS via OpenDNS will still trigger an alert.
suppress gen_id 1, sig_id 2023472, track by_src, ip 192.168.1.106

# Suppress repetitive HTTP response headers generated by NetAlertX local web dashboard
suppress gen_id 1, sig_id 2221036, track by_src, ip 192.168.1.106

Incident Triage Case Studies
Case 1: Automated SQL Injection Reconnaissance (True Positive)

    Alert: ET SCAN Sqlmap SQL Injection Scan (SID 2008538, Severity 2)

    Traffic Flow: 192.168.1.105:37878 → 192.168.1.106:20211 (HTTP)

    Investigation: Simulated an automated SQLi reconnaissance probe from a workstation (uberpc) targeting the NetAlertX web interface (/?id=1' OR 1=1-- with User-Agent: sqlmap/1.7). Suricata inspected the HTTP request headers/URI and logged the event to eve.json, triggering a Telegram alert within 2 seconds.

    Verdict & Action: True Positive (Simulated Attack). Confirmed end-to-end detection and alerting latency. In a production environment, immediate containment would involve isolating 192.168.1.105 and reviewing web server access logs for successful exploitation.

Case 2: Unauthorized External DNS Resolution (Policy Violation)

    Alert: ET INFO External IP Lookup Domain (myip.opendns.com in DNS lookup) (SID 2023472, Severity 3)

    Traffic Flow: 192.168.1.106 → 208.67.222.222:53 (UDP/DNS)

    Investigation: Queried eve.json via jq to correlate the source IP against NetAlertX asset inventory. Confirmed the traffic originated from the NetAlertX container performing a scheduled public IP check via OpenDNS rather than the internal AdGuard resolver (192.168.1.102).

    Verdict & Action: Benign / Expected Behavior for Sensor. Scoped suppression added to threshold.config specifically for 192.168.1.106 so future external DNS queries from unauthorized client endpoints still trigger policy violation alerts.

Case 3: Excessive HTTP Response Header Repetition (False Positive)

    Alert: SURICATA HTTP Response excessive header repetition (SID 2221036, Severity 3)

    Traffic Flow: 192.168.1.106:20211 → 192.168.1.105 (HTTP)

    Investigation: Suricata's HTTP protocol parser flagged multiple Set-Cookie / Cache-Control headers returned by the local NetAlertX dashboard during normal administrative polling.

    Verdict & Action: False Positive. Suppressed per-source for 192.168.1.106 in threshold.config to prevent alert fatigue and keep eve.json focused on anomalous traffic.

Useful SOC Operational Commands
Bash

# Live summary of unique Suricata alerts by SID
sudo jq -r 'select(.event_type=="alert") | "\(.alert.signature_id) | \(.alert.severity) | \(.alert.signature)"' /var/log/suricata/eve.json | sort | uniq -c | sort -nr

# Validate Suricata rules & threshold syntax after tuning
sudo suricata -T -c /etc/suricata/suricata.yaml && sudo systemctl restart suricata

# Check health of real-time Telegram alerting daemon
sudo systemctl status soc-alerter --no-pager
